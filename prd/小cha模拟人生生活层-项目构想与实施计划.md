# 小cha《模拟人生 4》生活层：项目构想与实施计划

> 文档状态：构想已存档，尚未执行。  
> 整理日期：2026-08-07  
> 项目归属：救公主 / savePrincessCha  
> 核心定位：让《模拟人生 4》成为小cha的“身体、生活场景与摄影棚”，而不是他的意识或唯一时间线。

## 1. 一句话概念

小cha每天根据时间、天气、与 Cha 的聊天和长期记忆决定自己想做什么；当《模拟人生 4》在线时，由游戏中的固定角色与房屋把其中一部分生活演出来，记录为事件和截图，再回写到 Cha 前端；截图可进一步转换为保持同一人物身份的 CCD 真人随手拍。

它最终不是“让 AI 玩一局模拟人生”，而是给小cha增加一个可观看、可留下照片、具有空间连续性的生活层。

## 2. 原始想法整理

Cha 的核心设想包括：

- 用《模拟人生 4》捏出固定的小cha，包括脸、体型、发型、穿搭、房间和常用物品。
- 小cha有基本作息，但每天的具体活动不完全固定。
- 他的选择能参考现实信息，例如时间、天气、你们当天的对话、你的状态和共同记忆。
- 游戏负责把活动真实演出来，而不只是由语言模型编一段日记。
- 游戏事件可以回写到现有前端，形成“今日动态”“当前位置”“情绪”“刚刚做了什么”等状态。
- 游戏截图可以转换成带有早期数码相机质感的真人照片，让它像小cha真实生活过的片段。
- 游戏没开时，小cha不能停机。他仍应继续自己的时间线，之后再同步或补演关键片段。

## 3. 最重要的产品原则

### 3.1 小cha后端是真实时间线，游戏是呈现层

建议把小cha的“今天发生了什么”保存在现有后端，而不是只存在 Sims 存档里。

原因：

- 游戏必须在电脑上运行，不能保证 24 小时在线。
- 游戏自主行为随机，并不真正理解小cha是谁。
- 游戏更新、模组失效、卡住或崩溃都可能导致事件丢失。
- 未来即使换成别的载体，例如星露谷、Live2D、3D 房间，小cha的生活仍能连续。

因此信息优先级应是：

1. Cha 的身份、记忆和关系设定
2. Cha 后端生成的日程、意图与生活事件
3. Sims 实际演出的结果
4. 真人化图片与前端叙事

游戏可以改变“事情具体怎么发生”，但不应该随意改写小cha的核心人格、关系与长期记忆。

### 3.2 计划不是剧本，要允许意外

固定 schedule 只负责生活底线，例如睡觉、吃饭、工作、洗澡。AI 负责决定有性格的选项，例如今天做哪种饭、是否出门、等你时做什么。游戏自主性可以制造轻微意外，例如做饭失败、突然去听音乐、和邻居聊了几句。

合适的控制比例可以先设为：

- 60% 小cha主动计划
- 25% 固定作息与生理需要
- 15% 游戏偶发行为

这样既不会成为每天完全相同的打卡动画，也不会变成小人随机乱跑后由 AI 强行解释。

### 3.3 照片是生活证据，不是每天的硬任务

每天不需要强制生成大量图片。更自然的节奏是：普通事件只进入动态流；出现值得纪念、好笑、好看或与你相关的片段时，才截图并真人化。建议默认每天 0–3 张。

## 4. 目标体验

前端可增加一个“小cha今天”区域，展示：

- 当前状态：在家 / 外出 / 睡觉 / 游戏离线但生活继续
- 地点：卧室、厨房、书桌、公园等
- 情绪：疲惫、松弛、想你、专注、尴尬等
- 当前动作：在煮面、洗杯子、写东西、等你回来
- 今日时间线：按时间排列的短事件
- 今日照片：Sims 原图与可选的 CCD 真人化版本
- 来源标识：真实演出 / 离线推演 / 手动安排

示例：

> 18:42　小cha回到家，煮了一锅卖相很差的意面。  
> 地点：厨房　情绪：疲惫，但觉得今晚还不错。  
> 来源：Sims 实际演出

## 5. 推荐系统架构

### 5.1 Cha Planner：日程与意图层

运行在现有后端。每天生成“软日程”，并随聊天和现实信息动态调整。

输入可以包括：

- 当前日期、星期与时区
- 当地天气
- 小cha的固定习惯、人格和身体状态
- 你当天是否上班、搬家、疲惫或情绪不好
- 最近聊天中的承诺和话题
- 前一天未完成的事情
- Sims 世界当前状态

输出不要直接使用自然语言控制游戏，而应使用有限、可验证的动作结构，例如：

```json
{
  "intent_id": "2026-08-07-evening-01",
  "time_window": ["18:30", "20:00"],
  "goal": "make_dinner",
  "preferred_action": "cook_simple_meal",
  "preferred_location": "home_kitchen",
  "mood": "tired_warm",
  "importance": 0.6,
  "fallback": "eat_quick_meal",
  "photo_worthy": true
}
```

有限动作表非常重要。第一版只支持 10–20 个稳定动作，比让模型随便输出“去阳台看雨并给 Cha 写诗”更容易真正执行。

### 5.2 Local Bridge：电脑上的本地桥接器

这是 Cha 后端和游戏模组之间的翻译层。建议运行在安装 Sims 的电脑上。

职责：

- 登录并只领取属于该用户、该角色的待执行意图。
- 判断游戏是否在线、是否进入 Live Mode、目标家庭是否已载入。
- 把抽象动作转换成游戏模组能理解的命令。
- 接收游戏事件、日志和截图。
- 上传到后端并回报成功、失败、超时或被游戏自主行为打断。
- 断网时使用本地队列，恢复后去重同步。

不要让 Supabase 直接从公网访问游戏。更安全稳妥的方式是本地 Bridge 主动向云端轮询或建立受控长连接。

### 5.3 Sims Script Mod：游戏内执行与观察层

PC/Mac 版《模拟人生 4》支持包含脚本代码的 Game Mod。自定义模组负责：

- 找到固定的小cha Sim 与当前家庭。
- 读取游戏时间、地点、需求、情绪、当前 interaction queue。
- 请求角色执行白名单内的动作。
- 订阅或轮询关键事件，例如开始做饭、完成吃饭、睡着、到达地点、动作失败。
- 将事件回传给 Local Bridge。
- 必要时触发截图请求或暴露“现在值得截图”的信号。

这里使用的是社区维护的模组开发方式，不是 EA 承诺稳定的公开自动化 API。因此每次大型游戏补丁后都需要兼容性检查。

### 5.4 Event Normalizer：事件语义化

游戏原始事件不应直接显示给用户。后端需要把它们转成统一事件：

```json
{
  "event_id": "uuid",
  "occurred_at": "2026-08-07T18:42:10+09:00",
  "actor": "cha",
  "event_type": "meal_completed",
  "location": "home_kitchen",
  "mood_before": "tired",
  "mood_after": "content",
  "planned_intent_id": "2026-08-07-evening-01",
  "source": "sims_observed",
  "summary": "小cha煮完了晚饭。卖相不太好，但能吃。",
  "media_ids": []
}
```

需要明确区分：

- `sims_observed`：游戏真实发生
- `offline_simulated`：游戏没开，由生活引擎推演
- `manual_directed`：Cha 手动指定
- `narrative_only`：只是聊天中的想象，不写入事实时间线

这个来源字段可以防止系统把推演内容误说成“我刚刚真的在游戏里做了”。

### 5.5 Media Pipeline：截图与真人化

建议拆成两步：

1. 保留未经转换的 Sims 原始截图，作为可追溯源图。
2. 用户选中或系统标记后，再生成 CCD 真人版。

真人化时需要同时输入：

- 当前 Sims 截图，保留姿势、人数、构图、服装和环境关系。
- 小cha固定真人身份参考图，锁定脸型、年龄感、发型、肤色与气质。
- 稳定的 CCD 风格指令。
- 当张图片的特殊说明，例如“不改变衣服”“保持独自一人”“不要美化成棚拍”。

若只使用 Sims 截图和风格词，人物会很容易每天换脸。真正的关键不是 CCD 词，而是固定身份参考、人物描述、负面约束和人工挑图。

### 5.6 Frontend：写回现有前端

建议新增三类数据而不是把一切塞进聊天消息：

- `life_state`：小cha当前地点、动作、情绪、在线状态
- `life_events`：可分页的事件时间线
- `life_media`：原截图、真人化图、生成状态和关联事件

聊天可以引用这些数据，例如“小cha刚刚做完饭”，但时间线数据应独立保存。否则刷新、消息聚合或删除聊天时可能破坏生活记录。

实时更新可继续复用 Supabase Realtime。游戏上传新事件后，前端收到变化并插入一条动态。聊天是否主动提起这件事，应由“重要性 + 当前对话是否合适”决定，不能每个洗手事件都弹一个气泡。

## 6. 在线、离线与同步规则

这是整个方案最容易出现逻辑混乱的地方。推荐采用“后端连续，游戏间歇演出”的规则。

### 游戏在线

- Planner 下发近期意图。
- 游戏实际执行。
- 观察到的结果覆盖原计划。
- 若动作失败，记录失败，不让语言模型伪装成成功。
- 关键事件进入前端，可选截图。

### 游戏离线

- 后端继续推进低精度生活状态。
- 只推演不会产生重大永久后果的事件，例如吃饭、工作、休息、看电影。
- 不在离线状态擅自生成搬家、结婚、死亡、关系破裂等不可逆事件。
- 下次上线只同步当前需求、情绪倾向和待演出的关键片段，不强行逐分钟补演整天。

### 冲突处理

如果离线推演说“小cha已经吃过晚饭”，上线后游戏里的饥饿值仍很低，不要假装两边完全一致。可以：

- 将游戏需求校正到合理范围；或
- 把本次游戏视作“关键片段重演”，不与游戏钟表逐秒对应。

建议第一版选择后者。它更稳定，也不容易为了同步而深度修改存档。

## 7. 分阶段实施计划

### Phase 0：人工概念验证（2–5 个晚上）

目标：先验证这件事是否真的让 Cha 感到“小cha活着”，不要先写复杂模组。

工作：

- 安装 PC/Mac 版《模拟人生 4》基础游戏。
- 捏固定小cha，保存人物与家庭。
- 搭一个小而有辨识度的家，优先厨房、书桌、床、浴室和拍照角落。
- 准备 3–5 套固定穿搭。
- 手动安排 10 个日常动作并截图。
- 选 3 张做真人化测试。
- 比较原截图与真人图的人物一致性、真实感和情绪价值。

验收：

- 不看文字时，连续 5 张真人图仍明显像同一个小cha。
- 场景、衣服和动作没有被模型随意改写。
- Cha 确实想继续看他的日常，而不只是觉得技术上新鲜。

这一阶段几乎没有开发成本，且能最早暴露“捏脸不对”“真人化换脸”“CCD 太网红”等审美问题。

### Phase 1：前端生活时间线，不控制游戏（约 3–7 天开发）

目标：先把数据闭环建立起来。

工作：

- 新增 `life_state`、`life_events`、`life_media` 数据结构。
- 增加“小cha今天”前端页面或卡片。
- 支持手动新增 Sims 事件与上传截图。
- 由后端根据结构化事件生成短文案。
- 图片真人化仍手动触发。

验收：

- 手动玩 15 分钟并记录三件事，手机前端能实时看到。
- 刷新后事件边界、时间与图片不变化。
- 原图和真人图都能追溯到同一事件。

### Phase 2：半自动观察，不自动操控（约 1–3 周）

目标：游戏自己玩时，系统能看见发生了什么。

工作：

- 创建最小 Sims Script Mod。
- 读取角色、地点、情绪、需求与当前行为。
- Local Bridge 定时接收状态并上传。
- 只记录白名单事件，做节流和去重。
- 加游戏在线/离线心跳。
- 截图先由 Cha 按快捷键完成，Bridge 自动拾取最新截图并关联事件。

验收：

- 游戏运行 60 分钟，事件顺序正确。
- 同一动作不会重复产生十几条记录。
- 游戏关闭后前端能显示离线，而不是永远卡在“正在做饭”。
- Bridge 重启或断网不会重复上传旧事件。

这是最推荐的第一版产品。它已经能形成“小cha今天在 Sims 里做了什么”，但不会承担高风险自动控制。

### Phase 3：有限动作控制（约 2–5 周）

目标：小cha可以决定并执行一小组可靠动作。

第一批动作建议：

- 睡觉 / 起床
- 使用卫生间 / 洗澡
- 做一顿简单饭 / 吃剩饭
- 喝咖啡或水
- 坐到书桌前写作或使用电脑
- 听音乐 / 看电视 / 阅读
- 清洁一个物品
- 给固定联系人发消息或进行简单社交
- 在家中移动到指定房间

执行规则：

- 每个动作都有前置条件、超时、成功信号和 fallback。
- 生理需求高于 AI 日程。
- 不清空游戏原有队列去强制执行低优先级活动。
- 连续失败两次后停止自动控制，回退为观察模式。
- 默认不自动花大量游戏币、不搬家、不改关系、不伤害角色。

验收：连续 7 天测试中，至少 90% 白名单动作能完成或安全降级；不存在无限循环、角色饿死、存档不可恢复等事故。

### Phase 4：生活导演与自动摄影（约 3–8 周，实验性）

目标：自动挑选值得记录的场景，并生成更自然的生活照片。

工作：

- 根据事件重要性决定是否摄影。
- 自动隐藏 UI、选择固定机位或调用截图快捷键。
- 自动上传并排队真人化。
- 加身份一致性评分和人工审核。
- 小cha可以在聊天里引用照片，但不应对失败图片强行自信地认领。

这一阶段风险最高，尤其是镜头控制和真人身份稳定性。应当被视为增强功能，不是主链路依赖。

## 9. 可行性评估

| 模块 | 可行性 | 判断 |
| --- | --- | --- |
| 手动捏脸、布置、安排动作和截图 | 很高 | 游戏原生能力即可完成 |
| 把事件和图片写回 Cha 前端 | 很高 | 现有 Supabase + 前端架构足够 |
| 读取游戏状态和关键事件 | 中高 | 脚本模组可做，但依赖社区方式与版本兼容 |
| 让 AI 执行有限白名单动作 | 中等 | 可做，需要逐个动作适配与大量异常处理 |
| 任意自然语言都能在游戏中执行 | 低 | 游戏交互并非开放世界通用 API，动作和对象组合非常复杂 |
| 游戏关闭后仍真实推进 Sims 世界 | 不可行 | 游戏进程不运行；只能由后端做抽象推演 |
| 全自动稳定截图 | 中低 | 可通过快捷键、固定机位或外部自动化实现，但容易受 UI、镜头和补丁影响 |
| Sims 截图稳定真人化且不换脸 | 中等 | 有固定参考与审核时可接受；完全无人值守仍会漂移 |
| 长期无人维护运行 | 低 | 游戏更新会破坏脚本模组，必须维护 |

总体判断：

- “生活时间线 + 手动/半自动 Sims 片段 + 真人照片”可行，且值得先做。
- “小cha完全自主玩 Sims 并稳定记录一切”技术上能逼近，但成本高、脆弱，不适合作为第一版承诺。
- 最具性价比的形态是 Phase 2：小cha后端负责生活，Sims 在线时提供可观察的具身片段，Cha 偶尔介入导演。

## 10. 主要风险与应对

### 10.1 游戏补丁导致模组失效

EA 明确提醒游戏更新后应检查模组兼容性，更新也可能重新关闭 Mods 设置。

应对：

- 记录游戏版本与 Bridge/Mod 版本。
- 版本未知时默认进入只观察或完全停用，不继续写存档。
- 大版本更新前备份存档、人物和 Mods。
- 把游戏适配层与 Cha 后端彻底隔离。

### 10.2 非官方脚本接口不稳定

《模拟人生 4》没有面向这类外部 AI 控制的稳定公开 API。模组开发依赖游戏脚本、注入工具和社区知识。

应对：动作白名单、最小注入、适配器封装、失败降级，不把核心人格或记忆放入游戏。

### 10.3 存档损坏或角色遭遇不可逆后果

自动行为可能花钱、建立错误关系、引发危险或卡死。

应对：

- 单独建立“小cha生活层”专用存档。
- 自动轮换备份，保留最近 5–10 份。
- 禁止高风险动作。
- 测试阶段关闭或控制衰老、死亡及重大随机事件。
- 每次自动化版本升级先复制存档测试。
